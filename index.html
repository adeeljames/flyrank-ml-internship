Ranking the Refresh Queue

A client-holdout study of which signals — staleness, visibility, position, or CTR — actually predict declining content, and whether a learned ranking beats a transparent hand rule on real FlyRank search data.

Abstract

Content teams have limited review capacity and need to know which pages to look at first. I built a Refresh / Content Opportunity Scoring pipeline on the FlyRank ML Internship dataset — a 30,000-page anonymized starter slice plus a 9.8-million-row verification cut of the full warehouse — to rank pages by likelihood of decline. A hand-written baseline rule (staleness × visibility) scored 0.620 Precision@50 under a client-holdout split; a Random Forest trained on ten observable signals scored 0.640 — a real but modest lift. The model's top predictors were raw visibility (impressions, position) rather than staleness, which my own signal audit had already flagged as an unreliable single-condition rule. The result is a ranked, reason-coded review queue, not an automated editing system, with explicit human-review and no-go rules attached.

§1

Introduction — the decision this supports

A content team cannot review every page every week. The practical question is not "is this page declining," in the abstract — it is: of everything in the inventory, which pages should a reviewer look at first? That is a ranking problem, not a one-off classification problem, and it is exactly the framing I committed to in Week 1 of this track.

I chose the Refresh / Content Opportunity Scoring lane. The unit of analysis is one content page, for one client, and the output is a ranked queue with a reason code attached to every row, so a reviewer can see not just that a page was flagged but why. The action a reviewer takes — refresh, rewrite title/meta, review, or monitor — is only ever a recommendation. Nothing in this pipeline edits or publishes anything on its own.

Methodology

Label

is_declining_label = (trend_direction == "down") — a current-window proxy, not a validated future outcome. I treat this explicitly as a starting point; a stronger label would use a prior-90-day feature window against a next-30-day decline outcome.

Signal audit (Week 4)

Before encoding any rule, I tested two signals against real FlyRank flag logic:

Staleness → refresh flags

Verdict: MIXED

Decline rate rose from 0.512 (<90d) to 0.611 (90–180d), then fell to 0.467 (180–365d, n=169) and 0.600 (365d+, n=5, too small to trust). No clean staircase.

CTR vs. position tier → CTR-fix logic

Verdict: CONFIRMED

CTR fell monotonically: 0.355 (page 1) → 0.334 (top 3) → 0.256 (striking) → 0.142 (page 3–5) → 0.055 (deep).

Baseline (Week 4)

One transparent rule: score = stale(180d+) × visible(500+ impr) × impressions_90d, reason code stale_visible_page. Precision@50 = 0.620 on a client-holdout test set. A top-10 review surfaced a real weakness: every one of the top 10 rows came from a single client, which meant the rule was letting one high-traffic client dominate the whole review queue.

Model (Week 5–6)

Logistic Regression and Random Forest, chosen for the same reason: the ranking output is the predicted probability, and a hand rule already showed 0.620 is a strong baseline to beat. Features: search_volume, word_count, impressions_90d, sessions_90d, content_age_days, days_since_last_update, avg_position, ctr, engagement_rate, scroll_rate.

Validation design

Client-grouped holdout (GroupShuffleSplit, 20% of clients held out entirely) — not a random row split. My Week-4 top-10 review showed pages from the same client can dominate a naive ranking; a random split risks leaking a client's pattern between train and test. Zero client overlap between train and test was confirmed programmatically.

Leakage audit

  • trend_direction / trend_pct excluded from every feature set — confirmed by assertion.
  • No FlyRank product decision flags used, at any stage.
  • Deliberate leak experiment (Week 3, on real warehouse data): adding the label-source column pushed a toy classifier's accuracy toward-perfect; removing it restored the honest number.
  • Unlike the reference FlyRank research paper's own Health-Score model — where Average Position and Impressions are both inputs and components of the target — my label is not a linear function of my features, so that specific circularity risk does not apply here.

days_since_last_update — the core signal my own baseline rule was built around — ranked 7th, at 4.5% importance. That lines up with the MIXED verdict from my Week-4 signal audit: staleness is real but weak on its own, and raw visibility (impressions, position, age) carries more of the model's decision.

Error inspection

18 of the model's top 50 recommendations (36%) were false positives. Every one of them shared a specific pattern: ctr = 0.00 despite real impressions (264–1,525) and a mid-range position (17–32). That is unusual enough — real impressions with zero clicks — to suggest a data-quality issue rather than genuine decline, and it is now a documented review step (see §6).

Honest read ROC AUC (0.598) and Average Precision (0.587) are modest — closer to random (0.500) than to a strong classifier. With ten observable features and a current-window proxy label, there is limited separable signal to find. The more promising next step is a better label — a genuine future-window decline outcome — not a more complex model.
§5

Limitations & honest framing

  • The label is a current-window proxy (trend_direction == "down"), not a validated future outcome.
  • Results are computed on a 30,000-row anonymized starter slice — not the full ~79M-row warehouse.
  • Model quality is modest (ROC AUC ≈ 0.60); treat scores as a rough prioritization aid, not a precise probability.
  • Nothing here proves a refresh causes recovery — that would require an experimental or causal design this dataset cannot provide.
  • Consolidation, seasonality, and SERP layout changes are not modeled — a "declining" flag could reflect any of these instead of genuine content decay.
  • This is decision-support for a human reviewer. It is not, and should not become, an automated editing or publishing system.

Ranked recommendations — the action playbook

Every row in the shipped queue carries a reason code and maps to one recommended action. Distribution across 30,000 pages:

Reason codeMeaningActionPages
declining_with_demandTrending down, 100+ impressionsrefresh13,136
monitor_onlyNo strong signal either waymonitor11,723
low_ctr_visible_pageRanks 1–20, CTR < 0.5, 500+ impressionsrewrite title/meta3,639
model_decline_riskModel probability ≥ 0.65review1,485
stale_visible_page180+ days stale, 500+ impressionsrefresh17

  1. Refresh mature, visibility-holding pages first

    Prioritize declining_with_demand and stale_visible_page rows — real audience already exists, so a refresh has somewhere to land.

  2. Fix titles and snippets on page-1 CTR laggards

    low_ctr_visible_page rows already rank — the fastest lever is often the click, not the content.

  3. Sanity-check zero-CTR pages before trusting the score

    Every documented false positive had ctr = 0.00 with real impressions — verify tracking before spending reviewer time.

  4. Treat monitor_only as "no action," not "no value"

    39% of pages land here. That is a finding, not a gap — most of the inventory doesn't need intervention this cycle.

Human review — required, always

  • Confirm the reason code against the underlying numbers.
  • Rule out consolidation — did a sibling page absorb this one's traffic?
  • Rule out seasonality before calling anything a "decline."
  • Skip any page under 100 impressions/90d — too little volume to trust.

What must NOT be automated

  • Auto-publishing AI-rewritten content from a score alone.
  • Auto-pruning "monitor" or low-score pages without human confirmation.
  • Using this queue for staffing or headcount decisions.
  • Treating any single score as proof a page needs work.
Monitoring & retrain triggers Re-score monthly, not continuously. Retrain if held-out Precision@50 drops more than ~15% relative to this paper's baseline (0.640), if a new data snapshot arrives, or if the label definition changes to a future-window outcome.
